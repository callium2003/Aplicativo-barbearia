## Lote 9 — CI e regressões obrigatórias

### Workflow

Foi criado:

```text
.github/workflows/ci.yml
```

O workflow roda em `push` e `pull_request`, com permissões somente de leitura (`contents: read`) e Node.js 24.

O job bloqueante `quality` executa:

1. `npm ci`;
2. `npm run typecheck`;
3. `npm test`;
4. `npm run lint`;
5. `npm run build`.

O workflow usa lockfile e não executa deploy.

### Regressões adicionadas

`tests/panel-context-and-access-guards.test.mjs` passou a cobrir também:

- falha de consulta de ownership não pode virar `role=null`;
- falha de consulta de membership não pode virar `role=null`;
- a resolução de papel deve falhar fechada em erros de Auth/PostgREST/RLS;
- a tela de agenda do barbeiro contém autogestão de disponibilidade;
- a UI utiliza `professional_hours`, `professional_breaks` e `professional_time_blocks` vinculados ao `professional_id`;
- a migration de RLS restringe autogestão ao próprio `professional_id`.

### Limite atual

A cadeia local de migrations ainda não foi reconstruída integralmente pelo Lote 0. Por isso o CI não executa `supabase db reset`, `migration repair`, `db push` ou testes contra o Supabase remoto.

Os testes RLS destrutivos/positivos/negativos continuam sendo executados controladamente em transações de homologação e revertidos quando são cenários de teste.

## Lote 10 — dependências e scripts de instalação

### Política

Não executar automaticamente:

```text
npm audit fix --force
npm audit fix
npm approve-scripts --all
npm approve-scripts --allow-scripts-pending
```

O último comando acima é proibido como aprovação em massa; para apenas listar pendências utiliza-se o modo de consulta configurado no script do projeto.

Atualizações de dependências devem ser específicas, revisadas e seguidas pelo job completo de qualidade.

### Auditoria contínua

O workflow ganhou um job separado:

```text
Dependency audit (informational)
```

Ele:

- executa `npm audit --json` usando o lockfile;
- não aplica correções;
- registra no GitHub Step Summary as quantidades por severidade;
- guarda `npm-audit.json` como artefato por 14 dias;
- é informativo (`continue-on-error`) enquanto as vulnerabilidades existentes são triadas individualmente.

Isso impede que uma vulnerabilidade conhecida seja "corrigida" automaticamente por atualização major sem teste, mas deixa a situação visível em cada alteração do repositório.

### Comandos locais adicionados

```text
npm run deps:audit
npm run deps:scripts:pending
```

`deps:audit` executa `npm audit --audit-level=high` sem `fix`.

`deps:scripts:pending` lista dependências com scripts de instalação ainda não cobertos pela política do npm, sem aprovar em massa.

### Scripts de instalação presentes no lockfile


Nenhuma dessas entradas foi aprovada automaticamente neste lote.

### Caso especial: esbuild 0.18.20

O lockfile mostra que `esbuild 0.18.20` entra por:

```text
drizzle-kit 0.31.10
  -> @esbuild-kit/esm-loader 2.6.5
     -> @esbuild-kit/core-utils 3.3.2
        -> esbuild 0.18.20
```

`@esbuild-kit/esm-loader` e `@esbuild-kit/core-utils` estão marcados como depreciados no lockfile.

A versão estável atual de `drizzle-kit` continua sendo `0.31.10`. Não foi adotado `1.0.0-rc`, fork ou pacote experimental apenas para eliminar a dependência antiga.

Além disso, Drizzle/D1 permanecem no projeto por herança do template e sua remoção deve ser coordenada com `worker`/build; não foi feita remoção isolada neste lote.
